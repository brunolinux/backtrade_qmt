# Design

## Context

动机见 `proposal.md`。`qmt_passorder.md` 定义内置 QMT、GBK、手工复制常量、09:35 前启动及分时买卖流程；用户进一步确认不进行资金估算，余额不足交由委托回调提示。

当前 `qmt_passorder.py` 已被用户删除，保留的 `qmt_passorder_xxx.py` 包含账户和交易日校验参考，但仍有行情订阅、动态重算、报价和资金预估、分钟窗口触发及全局异常停机。实施时重新创建目标文件，不覆盖该参考文件。现有测试覆盖回测与报告，尚无 QMT 执行测试。

## Goals / Non-Goals

**Goals:**
- 将配置校验、纯计划计算、定时提交和回调报告分开，使固定计划可在不连接 QMT 的环境验证。
- 兼容内置 Python 3.6，交易接口由 QMT 注入；导入模块时无交易副作用。
- 在回调可能与提交交错的情况下保持单次尝试语义。

**Non-Goals:**
- 不接入 MiniQMT、UI 自动化、外部 Excel、第三方日历或回测依赖。
- 不实现按资产比例缩放目标、资金预算、重试补单、等待卖出成交或报价择时。
- 不实现持久化去重、进程重启恢复、跨日调度或自动启动。

## Decisions

### 1. 单文件和显式状态

新建 `qmt_passorder.py`，保留账户与报告常量配置区，采用 Python 3.6 可用的标准库类型，不引入 dataclass 或新版本类型语法。北京时间通过标准库 UTC+8 时区生成，封装时钟便于测试。

配置和初始快照传入纯函数后返回新的计划，不修改输入。计划使用元组或命名元组组成的不可变记录，保存代码、方向和数量；阶段状态、已尝试标识及锁置于当前策略模块的普通全局运行状态中。QMT 会逐 bar 深拷贝和回退 `ContextInfo` 自定义属性，官方要求即时交易记录不得存放在该对象，因此运行状态不附加到 `ContextInfo`；后者仅用于调用 SDK。相比所有逻辑集中在定时器内，此划分可以直接验证初始差额与提交次数。

### 2. 初始化先校验再启动定时器

验证 `ACCOUNT_ID` 已替换占位符，日期为日期对象、目标为字典、代码符合范围，数量严格为整数（排除布尔值）、非负且整百。`TOTAL_VALUE` 为有限正数。

通过 QMT 交易日历确认当天及前一交易日，不读取文件或网络日历。设置账户，并查询 `ACCOUNT` 与 `POSITION`：账户快照必须唯一且完整，`m_dBalance`、`m_dAvailable`、`m_dInstrumentValue` 为有限非负数；持仓读取代码、交易所、总量和可用量，校验 `0 <= 可用量 <= 总量`，合并相同代码记录。`TOTAL_VALUE <= m_dBalance` 即通过资产上限校验，不拿可用余额约束买入计划。

QMT 官方文档限定 `get_trading_dates` 在 `after_init` 或 `handlebar` 调用，因此 `init` 只校验静态配置、设置账户；`after_init` 完成日历和账户校验及计划构建。初始化失败只报告原因并保持执行关闭，所有校验及计划构建完成后才注册 3 秒定时器。支持的使用方式仍为每日 09:35 前启动。

### 3. 从一次快照构建固定差额

对初始持仓和目标代码的并集计算差额。目标大于持仓则买入差额并按整百单位向下取整；目标小于持仓则以差额和可卖量的较小者为基础，部分减仓向下取整至整百。目标缺失或为零时清空实际可卖数量，允许完整清仓提交可卖零股。仅保留正下单量。

输出初始账户概况及固定计划；后续不查询行情、不刷新持仓以修改计划、不等待挂单结束。保留固定数量才能保证本次行为与用户确认的计划一致。极少数初始持仓零股造成的买入差额不足一手不下单，并在计划输出中说明。

### 4. 定时器只推进一次性阶段

定时回调比较当前北京时间与交易日期对应的阈值，使用严格大于关系。卖出阶段先于买入阶段判断；若定时器延迟至 09:36 之后，两阶段在同次回调按先卖后买执行，不引入成交等待。

锁内先认领阶段及标的尝试标识，锁外调用交易 API，以防重复定时调用及提交过程中同步触发回调。调用抛错也保持已尝试状态；逐笔捕获异常，继续同阶段其他标的。不能持有非重入锁调用 `passorder`，避免同步回调死锁。`handlebar` 为空操作。

仅采用内存标识，保证同一次运行内的单次尝试，不声称进程重启后恰好执行一次。

### 5. 按交易所提交即时成交剩余撤销委托

采用 `passorder`：买入 `opType=23`、卖出 `24`，数量方式 `orderType=1101`，ETF 数量单位为份。上海使用 `prType=42, price=0`，深圳使用 `prType=47, price=-1`；这些参数是对应市价类型要求的参数，不是用行情计算的成交限价。

使用 `quickTrade=2` 支持定时器直接提交，避免 `quickTrade=1` 的最新行情 bar 限制导致无订阅时不执行。通过策略名及包含交易日期、方向和代码的 `userOrderId` 关联回报，并在调用前登记标识。`passorder` 无成交结果返回，调用返回仅表示已发出调用。

不采用报价估算、余额预检、费用预留、资金占用状态或自动缩量。发生余额不足时保留原数量、报告错误并继续下一个标的。

### 6. 原生回调只报告，不驱动交易

提供 QMT 原生 `order_callback(C, orderInfo)`、`deal_callback(C, dealInfo)`、`orderError_callback(C, orderArgs, errMsg)`，并在初始化设置账户。按账户及本次登记的委托标识过滤，不处理其他策略回报。

委托回调报告受理、状态及拒绝原因；成交回调读取实际价格和成交份数，费用优先使用 `m_dCommission`，兼容 `m_dComission`，缺失时标记未知。委托错误回调按 `PassorderArguments.accountID` 和 `strategyName`（`策略名_&&&_投资备注`）关联已登记委托并报告错误文本；正常委托和成交则读取 `m_strAccountID` 与 `m_strRemark`。字段缺失不得导致回调异常中断其余委托；信息不全时打印可关联的已知信息。回调不修改固定计划，不触发补单。

### 7. 模拟验证与文档保持一致

使用 `unittest` 注入假的 QMT 账户、日历、定时器和下单函数，通过可控时钟验证边界、延迟和重复触发。模拟同步下单异常、异步拒绝、部分成交以及提交中同步回调；将任何行情订阅或报价调用设置为测试失败，保证无报价依赖。

验证文件可按 GBK 解码、兼容 Python 3.6 语法，导入不连接账户或提交委托；测试只捕获参数，不连接客户端。同步 `qmt_passorder.md` 说明固定计划、资金不足继续执行、费用可能未知和每日启动流程。

## Risks / Trade-offs

- 市价 IOC 可能部分成交或拒绝 → 明确报告实际结果，接受未达到目标且不追单。
- 固定计划与提交时实际持仓、可卖量或资金可能不同 → 按初始化计划提交，由券商处理有效性并报告错误，不动态重算。
- 进程重启会丢失尝试标识 → 文档限定每日启动一次，运行中重启由用户核对委托，不增加持久化状态。
- 客户端版本或券商通道的市价支持、回调字段可能不同 → 依据官方 API 编写参数及兼容读取，模拟测试不等于真实通道已验收。
- 部分成交回报不一定带最终完整费用 → 仅报告回报中可用费用或未知，不以估算填充。

## Migration Plan

1. 实施时新增目标脚本和模拟测试，保留用户参考文件，同步说明。
2. 本地运行定向测试及现有测试套件；检查 GBK 和内置 Python 语法兼容性。
3. 将脚本作为可审阅产物交付，本次不导入客户端或发送真实委托。用户日后按说明复制当日配置并自行部署。
4. 回退时停止 QMT 策略并恢复脚本；停止或恢复代码不代表撤销已发出的委托，已有委托须在客户端核对。
