# Design

## Context

参见 `proposal.md`。当前脚本严格按 GB2312 解码与编码均成功，但四行结构体注释的文字本身已经损坏，不能靠重新转换字节恢复。`_snapshot` 的文档字符串仍使用 `aggregated`，而持仓快照现在要求每个 ETF 代码只有一条记录。脚本第一行、说明文档与兼容性测试仍指定 GBK。

## Goals / Non-Goals

**Goals:**

- 用可读且准确的注释说明 `Holding`、`Snapshot`、`PlannedOrder` 的字段。
- 让源文件编码声明、实际字节、说明文档和测试一致指向 GB2312。
- 保持 QMT 策略可导入，并验证原有交易行为。

**Non-Goals:**

- 不改结构体字段、账户查询、委托计算、定时器和回调逻辑。
- 不扩展到仓库其他 Python 文件的编码迁移。

## Decisions

### 按已知语义重写损坏注释

从结构体定义、字段使用处及现有规格推断准确含义，重写四处乱码；不对已损坏的文本做反向编码猜测。`Holding.total` 是实际持仓份数，`available` 是可卖份数；`Snapshot` 记录账户资产、可用资金、持仓市值及逐标的持仓映射；`PlannedOrder` 记录带交易所后缀的代码、买卖操作号与委托份数。将 `_snapshot` 的 `aggregated` 改为与单标的单条记录一致的表述。其他文档字符串仅在与事实冲突时调整。

### 严格写入 GB2312

用明确的 `gb2312` 解码与编码处理脚本，编码时不使用替代字符或忽略错误；修改首行编码声明。实施后验证源文件能按 GB2312 严格往返，也能按 GBK 解码。相比仅替换首行声明，此法能验证新注释确实处于所要求的编码范围内。

### 同步文档及兼容性测试

将 `qmt_passorder.md` 中的 GBK 说明改为 GB2312，更新测试以按 GB2312 解码并检查编码声明及严格往返。保持 QMT 模拟下单测试关注可观察行为，不新增仅检查注释字面内容的测试。

## Risks / Trade-offs

- 新注释若含 GB2312 不支持的字符，编码会失败 → 使用严格编码，写入前先验证。
- 将源文件当 UTF-8 读写可能再次形成混合编码 → 以显式 GB2312 字节读写，并在修改后执行导入与完整测试。
- QMT 文档通常以 GBK 作为示例编码 → GB2312 字节属于其兼容子集；仍以目标客户端导入检查作为后续人工验收。

## Migration Plan

无需数据迁移。修改脚本、文档和测试后运行编码检查、QMT 定向测试与完整测试；若客户端导入不兼容，恢复这三个文件的变更并重新评估编码要求。
